# 双链路冗余语音上行

本开发分支将麦克风音频同时发往同一台电脑的已认证 Wi-Fi 与 BLE 链路，不叠加两者带宽。
任意一份及时到达即可播放；两份都丢失仍然算丢失。两种无线通信共享 ESP32-C3 与
2.4GHz 空口，发布前必须验证实机共存和内存。保留原单主链路的代码检查点。

## 协商与协议

认证后的 `pc.status` 声明 `voiceV2: 1`，设备只在 RAM 记录能力；
`device.hello` 也声明 `voiceV2: 1`。每次录音开始固定本次模式与电脑授权代次。
未协商时，固件继续发送原来 807 字节的 type-1 单主链路音频；桌面端仍接收旧固件格式。

V2 的 `voice.start`、`voice.end` 沿用双链路各发三次、共享递增 `eid` 的关键事件机制，
新增 `voiceVersion: 2` 与 `voiceSession`。后者为十六位小写十六进制随机非零 64 位录音标识。
结束事件还携带 `frames`，表示本次采集总块数，也是最后一个序号的后一位。两条链路音频内容相同：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 1 | 包类型 `6` |
| 1 | 8 | 录音标识，小端 |
| 9 | 4 | 块序号，小端，从零开始 |
| 13 | 804 | 独立 IMA ADPCM 块，16kHz 单声道 1600 个采样 |

UDP 与 BLE 分片内的完整包均为 817 字节，包含类型字节。保留原 180 秒录音上限。
V2 拒绝大于等于 2000 的块序号及超过 2000 的总块数，为录音上限保留余量，同时限制畸形输入。
一次录音内序号不回绕。仅授权端点可以发送业务音频；沿用可信局域网安全模型，没有新增 UDP 鉴权。

## 独立发送与有界缓存

采集任务每 100ms 编码一次。Wi-Fi 附着新鲜时，用独立包缓冲立即提交 UDP；内核接收发送请求后，
将同一份数据放入一个 BLE 待发槽并唤醒现有网络任务。新包覆盖未发送副本会计数。
不新增任务、堆分配音频队列，也不扩大 NimBLE 缓冲池。

网络任务先取走副本再发送，不会跨蓝牙操作持有副本互斥锁。一个静态在途槽与一个待发槽
约占设备 1.7KB RAM，另有互斥锁与计数器。副本绑定电脑授权代次、BLE 连接代次，
授权失效、蓝牙句柄复用或超过 200ms 的副本会被丢弃。UDP 提交失败或仅有 BLE 时，
保留原有有限等待的直接蓝牙发送。直接发送或工作任务发送失败后，可以利用原有待发槽位重试，
但不能延长该副本最初的 200ms 有效期，旧重试不能覆盖更新的待发帧，电脑授权或蓝牙连接代际失效时不再重试。
仅在有待发副本时，将工作任务轮询间隔限制在 20ms 内，覆盖录音末尾。进入槽位不代表送达，
应另外检查电脑实际收到和播放的唯一帧计数。UDP 内核提交成功不等于送达，Wi-Fi 单向故障仍需依靠冗余副本。

Type 6 与 type 1 使用相同语音缓冲准入策略：保留六个总 mbuf 块和四个实际使用池内块，
整包发送等待预算为 30ms，并包含发送锁等待。控制消息短暂占锁时，
语音在现有预算内等待，避免蓝牙单链路上的正常音频立即被丢弃。每个蓝牙分片连同分片头都放在实际分配的单个 mbuf 可用空间内，
避免满 MTU 分片串联占用两个小池缓冲块，而另一个池仍有空闲。接收端原本就支持可变分片长度。
一条链路故障不清除配对授权，也不要求重新配对。
收音机及配置同步协议保留原有行为。

## 电脑合并与生命周期

### 单链路丢块补发

经过授权的桌面端在 `pc.status` 中声明 `voiceRepair: 1`。V2 录音开始时，设备按需申请四块压缩音频历史，
申请时为控制和编解码保留至少 12 KiB 的 8 位堆空间。申请失败可退为两块，再失败则关闭补发，保留原有语音能力。
`voice.start` 的 `voiceRepair` 返回实际缓存容量，`voiceLinks` 返回已授权链路位图（Wi-Fi 为 1，蓝牙为 2），旧端保持原行为。四块历史占用小于 3.6 KiB，
连续开始下一段录音时可以复用，正常结束 450ms 后或电脑授权代际改变时释放。待机没有历史缓存申请、确认定时器或额外任务。

如果没有成功的蓝牙兜底，UDP 的 `ENOMEM`、`ENOBUFS` 和暂不可写错误进入本地重试：最多八次，
失败重试之间至少间隔 20ms，不能在该帧最初生成 200ms 后启动重试。采集任务不等待重试完成，进入队列不代表送达。

对已经提交给链路、但电脑未收到的音频，桌面端只请求当前播放窗口中的缺失序号，覆盖开头与末尾。
`voice.repair` 使用原有 device/client/token 授权字段，携带十六位 `voiceSession` 和一至四个整数 `frames`。
只有当前已授权端点能够请求补发；补发不能抢占电脑连接、延长租约，也不进入应用指令队列。
设备拒绝过期、已被覆盖或属于旧录音的历史。双链路重复请求会合并，每帧有 60ms 冷却及最多两次请求额度。

电脑最多每 60ms 发一次请求，每个缺块最多请求两次。补发提交失败后，在该帧最初生成后的 400ms 内最多尝试三次。
补发复用现有网络任务，录音期间每 20ms 轮询。链路正常时没有补发请求。电脑本地提交失败不扣除缺块的两次请求额度，但仍遵守全局发送间隔。
补发沿用 type 6 格式，在解码前去重；停止、休眠、断开、授权丢失或开始新录音时清除电脑补发状态。

Wi-Fi 和双链路保留 120ms 起始缓冲；协商补发能力后的纯蓝牙录音使用 160ms，为连续两块丢失的反馈往返留出时间。
每段录音额外等待仍最多 200ms，因此主动缓冲分别不超过 320ms 或 360ms，不含采集、传输和系统输出。
超出有限恢复窗口的持续中断仍可能丢失音频；补发不会无限积压，也不会自动重新开始输入。

桌面端在入队前校验包头、ADPCM 块和当前录音标识。压缩重排窗口最多保留八块音频。
每个序号第一份到达的数据胜出，后续副本不解码，也不刷新语音看门狗。
首包预缓冲 120ms（协商补发后的纯蓝牙为 160ms），随后每 100ms 播放一块，仅录音期间运行 20ms 定时器。
未启用补发时，首次播放跳过缺失的开头块；启用补发时，设备仍保留的开头缺块可以使用与中间缺块相同的有限补救等待。

开始播放后，缺失块可共享本次录音总计不超过 200ms 的额外等待。等待时输出自然暂停，
此时到达的首份副本仍可保留语音内容，而不是整块删除。预缓冲与补救等待合计最多 320ms（纯蓝牙补发为 360ms），
不含采集、传输和系统音频队列；预算不会在每次丢包后重置。用尽预算后缺失块才用静音补位，迟到副本丢弃。
较大序号跳跃或调度停顿会重新对齐窗口，不积压播放数秒前的旧语音。
结束块数限制尾部静音并计算收尾等待，上限一秒。音频包不能自行开始录音。
按设备 ID 与启动标识记录事件顺序，阻止迟到开始事件重新打开已结束录音；
会话标识阻止旧结束事件停止下一段录音。

V2 的控制主链路仍按持续无响应或明确断开切换；语音已经双发，不再因音频丢包反复改变路由。
旧协议录音保留原切换策略。四点五秒无新音频释放快捷键、权限丢失处理、录音时限，以及
断开／休眠／退出时立即停止的保护不变。录音结束即释放合并定时器与缓存，空闲期间不新增周期音频任务。
正常收尾期间收到的回车最多暂存八次，释放语音快捷键后再执行；镜像副本仍去重。
异常停止会丢弃暂存回车，避免断开或休眠后出现延迟输入。

## 验证与诊断

主机测试直接运行生产 C 发送代码，覆盖蓝牙阻塞、覆盖副本、过期、授权代次失效与单链路操作。
C 生成的协议包由 Swift 解析，并逐采样对照解码。时间线测试覆盖去重、互补／共同丢包、
乱序、开头缺包、旧会话、结束块数、调度停顿与缓存上限。
仍需通过原主机／固件完整检查和桌面端收音机、权限、休眠回归。

日志分别记录采集块数、UDP／BLE 提交数、被覆盖／过期副本、两条链路收到的副本、
合并接纳数、重复、迟到、补齐空洞、错过播放的块、补救次数、额外等待和重新对齐次数。
实时副本发送不做周期控制台输出，设备累计计数在采集结束后报告；常规内存／栈报告也避开音频期间。
桌面端每秒最多在后台刷新一次音频设备状态，音频包处理不再枚举 CoreAudio 设备，
仅音频数据引起的界面更新最多每秒五次；休眠使旧查询结果失效。
语音期间临时申请允许系统／显示器休眠的低延迟调度，所有停止路径均在释放音频前结束该活动。
首份副本到达间隔与首次迟到计数，用于区分错过播放时间和始终未到达；迟到重复副本不代表无线丢包。
桌面端已见序号集合受每段 2000 块上限约束。
补齐空洞数不等于无线丢包率。日志不记录音频、凭据或用户说话内容。

实机需对比仅 Wi-Fi、仅 BLE、双链路的相同长录音，覆盖录音期间断开任一链路、
双断与恢复。检查语音／回车、内存最低余量、ATT 压力、无线共存、尾字、电脑休眠，
以及电台暂停／恢复。模拟通过不能证明真实无线可靠性，也不代表完成实机长稳测试。
